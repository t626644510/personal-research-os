# P01.5 Hover Encyclopedia UI Validation

Status: ready for human evaluation

Baseline: `986359b69aca6b1a3cfe77c7ae1c634f00aae38b`

## What was implemented

- Added four realistic accelerator/RF reading notes under `00_Inbox/notes/`. They use canonical Concept names and aliases in ordinary technical prose.
- Added `99_Meta/tools/hover_ui.py`, a standard-library command that sends Markdown text through the existing `hover_resolver.py` and writes one self-contained HTML snapshot.
- Highlighted every resolved mention and attached a compact hover/focus card containing only the canonical Concept name, Hover Summary, optional Category, and optional Related concepts.
- Added keyboard focus support and safe HTML escaping so the same cards can be evaluated without a mouse and Markdown content is not executed as HTML.
- Added tests for local index use, alias resolution in the example notes, card content, output escaping, and absence of network resources.

The P01 architecture remains unchanged:

```text
Concept Markdown -> concept_tools.py -> concept_index.json -> hover_resolver.py
                                                        -> hover_ui.py -> local HTML
```

`hover_ui.py` is a disposable validation consumer. It does not write Concept data, alter the index contract, or become part of the knowledge-generation workflow.

## How to evaluate

From the repository root, regenerate the index and open one note:

```powershell
python ResearchOS/99_Meta/tools/concept_tools.py scan
python ResearchOS/99_Meta/tools/hover_ui.py "ResearchOS/00_Inbox/notes/HOM impedance reading note.md" --open
```

Repeat with the other notes in `00_Inbox/notes/`. Hover over highlighted terms and use Tab to inspect the same cards with keyboard focus. Record observations before changing match rules or summaries.

## Current limitations

- This is a static HTML snapshot, not an Obsidian plugin. Regenerate it after editing a note or `concept_index.json`.
- The viewer preserves escaped Markdown source and whitespace instead of implementing full Markdown rendering. It validates hover behavior, not visual parity with Obsidian.
- Matching retains the P01 behavior: terms inside frontmatter, code, link targets, or other Markdown syntax may be highlighted.
- Every recognized occurrence is highlighted. There is no density threshold, first-mention-only mode, or per-note suppression control.
- Tooltip placement is CSS-only and intentionally simple; a card near a narrow viewport edge may not be ideally positioned.
- Related concepts are plain labels in the card. They do not open nested cards or Concept pages.
- The generated page contains only the index snapshot available at generation time; it does not watch files for changes.

## Questions for human evaluation

1. Are hover cards too frequent in normal accelerator notes?
2. Is the Hover Summary length appropriate for a quick memory trigger?
3. Is the current Concept granularity correct, or do cards appear for terms that are too broad or too narrow?
4. Does highlighting and hovering improve reading efficiency compared with opening Concept notes manually?
5. Are canonical names clear when the highlighted text is an alias such as `Qext`, `QL`, `R/Q`, or `wake field`?
6. Are Category and Related concepts useful in the compact card, or do they add distracting visual weight?
7. Should only the first mention in a paragraph or section be highlighted?
8. Is keyboard focus behavior sufficient for evaluation without a mouse?

## Phase boundary

Do not use this validation result to add AI calls, RAG, embeddings, a vector database, a crawler, automatic knowledge generation, or a full Obsidian plugin during P01.5. The next decision should be based on recorded human reading feedback.
