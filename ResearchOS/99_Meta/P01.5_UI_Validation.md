- 新增 `99_Meta/tools/hover_ui.py`：使用 Python 标准库把 Markdown 交给现有 `hover_resolver.py`，并生成单个自包含 HTML 快照。
- 高亮全部识别出的概念，并附加紧凑的 hover/focus 卡片；卡片只显示概念名称、悬浮摘要、可选分类和相关概念。
- 支持键盘聚焦和安全 HTML 转义，既可不用鼠标评估，也不会把 Markdown 内容当作 HTML 执行。
- 增加本地索引、中文 alias、卡片内容、HTML 转义、离线资源和 CLI 打开行为测试。
- HTML 界面、状态文字、CLI 帮助和生成结果提示已改为中文，页面语言为 `zh-CN`，并使用中文字体栈。
- 卡片优先显示“中文 alias（英文 canonical name）”，分类只在 UI 展示层转换为中文。

P01 架构保持不变：

```text
Concept Markdown -> concept_tools.py -> concept_index.json -> hover_resolver.py
                                                        -> hover_ui.py -> local HTML
```

`hover_ui.py` 是可丢弃的验证消费者。它不写入 Concept、不改变索引契约，也不参与知识生成流程。

## 语言与身份约定

- `id` 和英文 canonical name 是稳定机器身份。
- 中文术语、缩写和历史名称通过 `aliases` 多对一指向 canonical name。
- Concept 文件名、H1 和索引键不做批量中文重命名。
- `Hover Summary` 等 Schema 标题保留英文，标题下的知识内容以中文为主。
- `category` 的英文值保留在数据层，由 UI 使用固定映射显示中文；未知分类原样显示。
- 中文 alias 不采用模糊匹配，并避免单字或过宽术语。

## 评估方法

在仓库根目录重新生成索引并打开一篇笔记：

```powershell
python ResearchOS/99_Meta/tools/concept_tools.py scan
python ResearchOS/99_Meta/tools/hover_ui.py "ResearchOS/00_Inbox/notes/HOM impedance reading note.md" --open
```

依次替换为 `00_Inbox/notes/` 中的其他样例。将鼠标停在高亮术语上，并使用 Tab 键检查相同卡片的键盘聚焦行为。在修改匹配规则或摘要前，先记录人工阅读反馈。

## 当前限制

- 这是静态 HTML 快照，不是 Obsidian 插件；修改笔记或 `concept_index.json` 后必须重新生成。
- 查看器保留经过转义的 Markdown 源文本和空白，没有实现完整 Markdown 渲染；它验证 hover 行为，而不是复刻 Obsidian 视觉效果。
- 匹配仍沿用 P01 行为：frontmatter、代码、链接目标或其他 Markdown 语法中的术语也可能被高亮。
- 每一次识别到的出现都会高亮，目前没有密度阈值、仅首处高亮或单篇抑制控制。
- Tooltip 定位仅使用 CSS；在较窄视口边缘，卡片位置可能不理想。
- 相关概念只是卡片内的标签，不能展开嵌套卡片或打开 Concept 页面。
- 页面只包含生成时的本地索引快照，不监听文件变化。
- 中文没有天然词边界，过短 alias 仍可能产生子串误命中。

## 人工评估问题

1. 在普通加速器技术笔记中，悬浮卡片是否出现得过于频繁？
2. 中文悬浮摘要的长度是否适合作为快速记忆提示？
3. 当前 Concept 粒度是否合适，是否有过宽或过窄的术语触发卡片？
4. 与手动打开 Concept 笔记相比，高亮和悬浮是否提高了阅读效率？
5. 当命中文本是 `Qext`、`QL`、`R/Q`、`尾场` 等 alias 时，“中文 alias（英文 canonical）”是否足够清晰？
6. 分类和相关概念对紧凑卡片是否有帮助，还是增加了视觉负担？
7. 是否应只高亮每段或每节中的第一次出现？
8. 键盘聚焦是否足以支持无鼠标评估？
9. 中文 alias 是否出现了明显的子串误命中？
